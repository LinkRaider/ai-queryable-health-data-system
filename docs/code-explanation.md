# Code defense: understand the whole system
A practical English guide to the implemented five-operation system. Module names below are relative to src/health_data/. Read the cues first; use the explanation to reconstruct the behavior rather than memorize symbols. A contract means accepted inputs, their meaning, outputs, and failure guarantees.

## 1. Start with the core, not the model
**Cues:** synthetic observations → retained JSONL → transactional ingestion → PostgreSQL analytics → optional HTTP and English interface.
**Say it:** “The system creates a fixed synthetic heart-rate sample, retains the original events, and loads them idempotently. The query engine answers a small set of explicitly defined questions. HTTP and the local model adapt requests to that engine; neither owns a second calculation.”
**What and why.** The default GenerationConfig selects 50 users over 21 days, from 5 October 2026 at 00:00 UTC to 26 October at 00:00 UTC, including 5–25 October under `[start,end)`. These are synthetic engineering patterns, not clinical measurements or a device specification; that remains true for dates still in the future when the demo is prepared. Restarting the program does not append today's data. The maximum query range is separately 31 days: asking for more dates does not create observations.
**Objects versus work.** GenerationConfig holds the seed/window/population; UserProfile holds stable individual tendencies; DayPlan holds a local day's schedule; HeartRateEvent holds one reading. EventSource describes published input. IngestionResult reports durable and attempt-level progress. StructuredQuery carries a bounded question; QueryResult carries its answer. Functions transform these objects. Settings collects configuration; TemporalInterpretation records the date decision, and NaturalLanguageInterpretation combines it with a query.
**Python you need to defend.** @dataclass generates initialization, representation and equality methods. frozen=True blocks normal field reassignment, so config.seed = 3 fails; GenerationConfig(seed=1) and GenerationConfig(seed=2) still have different values. It is not deep immutability: an EventSource.configuration dictionary remains mutable. slots=True provides declared instance storage and normally removes the instance __dict__; it is not runtime type validation or a ban on subclasses. Explicit __post_init__ checks and Pydantic perform validation where implemented.
**Useful mechanics.** @property calculates values such as window_end and timezone on access. StrEnum gives named text values, not a parser that validates every annotation. A Protocol specifies the planner methods without requiring inheritance. yield emits events gradually; _batches makes bounded lists. This is not constant memory end-to-end: source validation retains unique IDs and several tests/scripts materialize events. Context managers close resources or commit/roll back transactions; finally handles cleanup on failure. raise ... from error preserves a technical cause.
**Navigate.** __init__.py exports public generator types/functions through __all__. The implementation uses a src package layout: install the package to import health_data; tests and the sample script also add src to their import path. Do not start by explaining the model as if it creates measurements or writes SQL.

**Focused evolution.** Measure capacity and backup/restore first; add partitioning for demonstrated pruning/retention needs, Parquet for justified large scans/archival, or a lakehouse only for actual shared-lake/multiple-engine needs. Continuous arrivals need ongoing producer/consumer handling; Kafka is conditional on retained replay, backpressure or independent consumers, not a mandatory upgrade. Separate core/inference readiness and first-request reliability also need work. Removing HTTP/NL bonuses would retain generation, source, ingestion, SQL and CLI queries but require edits to CLI/config/Compose/dependencies/tests/docs, not merely deleting two modules. That simplification is a proposal, not an applied change.

## 2. generator.py: build people and their local days
**Cues:** stable person → date-specific plan → priority rules; duration is not sampling cadence.
**Say it:** “A profile is a repeatable set of tendencies, not an identical schedule every day. A separate day seed varies wake time, bedtime and optional activities. At each cursor instant the generator chooses the highest-priority state, then creates a reading only if the device is on.”
**Profiles — generate_profiles.** IDs are user-0001/device-0001 onward, with one device per user. Named zones cycle through America/Los_Angeles, America/Denver, America/Chicago, America/New_York and Europe/London. ZoneInfo supplies local calendar/offset rules; the generator advances its cursor in UTC and converts to the profile zone to choose behavior.
- Resting baseline is uniformly drawn from 52–78 BPM, rounded to one decimal. Ordinary activity adds a profile-specific 18–38 BPM; workout boost is 62–108 BPM, also rounded.
- Profile wake time is an integer minute from 06:00–08:30; profile bedtime is 21:30–23:45, both local.
- Each profile receives a workout probability from 0.25–0.72 and device-off probability from 0.18–0.48. These are per-day chances for that individual, not a promise that every user works out or removes the device every day.
**Daily plan — build_day_plan.** A stable random generator keyed by seed, user and local date adds independently drawn −20 to +20 minutes to the profile wake/bed times. Wake is clamped to 05:30–09:00, bedtime to 21:00–23:55. Distinguish the code's clamp guards from the profile-plus-jitter envelope: wake can actually reach 05:40–08:50 under these profile defaults; bedtime can reach 21:10–23:55. _at_local_minute constructs a local datetime.
- If its probability draw succeeds, one workout starts at an integer minute between wake + 90 minutes and bed − 90 minutes. Its duration is 25–70 minutes. That is the workout's length, not the interval between retained readings.
- If the off draw succeeds, one device-off interval starts between wake + 30 minutes and bed − 45 minutes. Its drawn duration is 35–125 minutes; its end is clipped at bedtime. The final interval can therefore be shorter than the drawn duration.
**State selection — _state_at, in exact priority order.** Device off wins over workout; workout wins over sleep; sleep wins over rest; otherwise ordinary_activity. Off returns None, not another ActivityState. TimeWindow.contains includes start and excludes end.
**Rest means awake rest, not sleep.** Before wake or at/after bedtime is sleep. Within awake time, rest applies during the first 45 minutes after waking, the final 45 minutes before bed, 12:00–13:00 and 18:30–19:30 local. Morning uses minutes_after_wake < 45; evening uses minutes_before_bed <= 45. Lunch/evening windows exclude their end minute. Workout overrides these windows, and off suppresses even a workout reading. The minute-based rule includes all seconds within each selected minute.
**Why these choices.** Profiles and schedules create distinguishable patterns and explicit missingness. They are chosen simulation rules, not evidence of wearable physiology. device_off_windows rebuilds overlapping local plans for gap inspection, including partial local days at the UTC window edges.

## 3. generator.py: readings, values and reproducibility
**Cues:** choose state → generate BPM → yield event → advance cursor.
**Say it:** “The state controls both the value distribution and how often a record is retained. A workout lasts tens of minutes but emits readings seconds apart. A device-off interval creates missing observations, never zero BPM.”
**Reading cadence — CADENCE_SECONDS and generate_events.** After emitting a reading, the UTC cursor advances by the current state's cadence plus a uniformly drawn integer jitter:
- sleep: 300 ± 40 seconds, so 260–340 seconds between scheduled cursor positions;
- rest: 180 ± 30 seconds, so 150–210 seconds;
- ordinary_activity: 75 ± 15 seconds, so 60–90 seconds;
- workout: 20 ± 5 seconds, so 15–25 seconds.
The state is recomputed at the next cursor. The loop does not force an observation exactly at each state boundary. When the cursor lands inside an off window, it jumps to the off end plus 1–30 seconds and checks the state again; it may pass the generation end. Consequently gaps across an off interval are not constrained by the ordinary cadence ranges. These are application-record intervals, not a claim about sensor-internal sampling.
**Values — _heart_rate_value.** Let B be the user's baseline. A circadian term is 1.8 × sin((local hour − 9) × π / 12) BPM; it uses the integer local hour, not a continuously varying minute value.
- Sleep draws a normal value with mean B − 7 and standard deviation 2.2 BPM.
- Rest draws around B + circadian with standard deviation 3 BPM.
- Ordinary activity draws around B + ordinary boost + circadian with standard deviation 7 BPM.
- Workout uses elapsed time divided by planned duration, clamped to 0–1. The boost multiplier is 0.72 + 0.28 × sin(progress × π): lower at the edges, highest halfway through. It draws around B + workout boost × multiplier with standard deviation 7.5 BPM. This is a synthetic warm-up/effort curve, not a measured training model.
Every final value is clamped to 30–220 BPM and rounded to one decimal. Noise allows individual readings to overlap between states; the state means are patterns, not a rule that every workout value exceeds every rest value.
**Identity and randomness.** _stable_seed hashes joined seed inputs with SHA-256 and takes the first eight bytes, avoiding Python's process-randomized hash(). Separate random streams for profiles, day plans and per-user events stop repeated day-plan lookup from consuming the event stream. The event stream includes config.identity, which includes schema/generator versions, seed, canonical window and user count.
**Event payload.** HeartRateEvent carries schema_version, event_id, user_id, device_id, observed_at, metric, value, unit and activity_state. as_dict renders UUID/enums/timestamps for JSON. canonical_timestamp requires an offset, renders seconds and uses Z for UTC. _event_id uses UUIDv5 with a fixed namespace and schema, seed, window, user, device and timestamp; it is repeatable identity, not a secret or random counter. The payload value is not part of that identity: conflicting content must therefore be checked during ingestion. GenerationConfig rejects naive start times and nonpositive days/users. Determinism aids tests; real recovery still requires retained original events.

## 4. source.py: publish once, validate, replay the original
**Cues:** bytes plus metadata; complete pair; fail rather than silently replace published input.
**Say it:** “ensure_source either validates and reuses a compatible published source without calling the generator, or creates the first source. Recovery then rereads its actual JSON lines. It does not regenerate missing measurements from a seed.”
**How publication works.** publish_source serializes each event as a compact, sorted JSON object plus newline into a same-directory staging file. While streaming it calculates the SHA-256 of the exact bytes, total line/event count and unique UUID count. It flushes and fsyncs the file, then os.replace publishes the JSONL filename. _write_json_atomic separately writes, flushes, fsyncs and renames its metadata sidecar. Cleanup removes leftover staging files when possible.
**Why a sidecar.** metadata_path_for appends .metadata.json to the JSONL suffix. The sidecar contains format version, source_key, configuration, event_count, unique_event_count and sha256. source_configuration fixes schema/generator version, seed, canonical bounds and population; source_key hashes its canonical JSON. This separates “which requested dataset?” from “which exact bytes?”. Duplicate lines can make total count exceed unique count.
**Reuse decision.** If both files exist, _validate_existing_source requires supported format, exact requested configuration and matching source key. It rejects invalid metadata types/counts, including booleans masquerading as integers. It reads the bytes to verify line count and digest, then parses all events to verify unique count. Successful reuse sets EventSource.reused=True and never invokes event_generator. Incompatible or corrupt published pairs raise SourceError without silently replacing them. If only one file exists, the design treats it as an interrupted initial publication and replaces the incomplete source.
**Line validation — read_events and _parse_event.** Reading is UTF-8, one JSON object per line. The parser requires exactly the nine event fields, supported schema/heart_rate/bpm/state, UUID text, complete user/device patterns and the configured corresponding pair. The timestamp must have seconds and an explicit offset in the accepted RFC 3339 shape, and must parse as a real date/time. Numeric values exclude bool, infinity and NaN; they must be within 30–220 and have at most one decimal place. The canonical UUIDv5 is reconstructed from the event identity and configuration and must match.
**Failures are useful.** “Invalid source line 2: malformed JSON” locates a repairable data problem; invalid UTF-8, field sets, precision or canonical identity receive analogous line-specific errors. Metadata/file read errors, incompatible configuration and digest mismatch are source-level errors. Digest validation establishes unchanged bytes, not authenticity; someone who can rewrite both files is not stopped by an unsigned hash. Parsing and database checks are complementary, not interchangeable.
**Limits to acknowledge.** JSONL rename and sidecar rename are two operations, not one atomic two-file transaction. A complete pair is the completion marker. File fsync is not proof of host-loss durability or a backup. Initial concurrent publication is not coordinated by the later database lock. Reuse validates the complete source before ingestion, but a later mutation can still fail while replaying; retain immutable input operationally. The parser checks the implemented event contract, not a clinical model or every possible schedule invariant.

## 5. db.py and sql/schema.sql: safe retry, not a positional checkpoint
**Cues:** one snapshot; cooperating-writer lock; insert then compare; commit one batch.
**Say it:** “The database remembers accepted events and source identity. Retry rereads from the beginning. Exact duplicates are harmless, different content under an existing identity is an error, and one failed batch cannot erase previously committed batches.”
**Schema purpose.** users stores user/device identity, named zone, baseline and profile JSONB. The pair is UNIQUE. heart_rate_observations stores the event fields plus ingested_at: UUID primary key, timestamptz for instants and numeric(4,1) for one-decimal BPM. CHECK constraints restrict version, metric, units, activity state and value range. Its composite foreign key prevents pairing a user with the wrong device. Its natural UNIQUE key is (user_id, device_id, observed_at, metric): a different UUID cannot create a second reading at that identity.
**Access paths.** The user/time/activity index serves single-user time filters; the time/activity/user index serves population time scans. Both INCLUDE(value), which can support index-only access if the plan and visibility allow it; no guarantee of a particular execution plan is claimed. Indexes cost storage and writes. A single indexed table fits the current small fixed sample; partitioning would need demonstrated retention or query-pruning value.
**Ingestion setup.** connect uses psycopg dictionary rows. apply_schema reads SCHEMA_PATH and commits the schema. ingest rejects invalid batch size or negative delay, obtains a session PostgreSQL advisory lock and commits the lock-acquisition transaction. This serializes cooperating ingest calls across batch commits, not arbitrary database writers or prior source publication. It checks ingestion_runs for the source key. A different snapshot requires an isolated database. The saved configuration includes source_sha256, so changed input bytes cannot silently reuse the same run.
**Each batch.** _insert_profiles adapts dataclasses to SQL/JSONB; _batches supplies lists of up to the configured size, default 1,000. In connection.transaction(), executemany uses bound parameters and INSERT ... ON CONFLICT DO NOTHING. Then _assert_batch_matches_database fetches every batch UUID and compares all persisted event fields. Decimal(str(value)) aligns comparison with PostgreSQL numeric rather than a float's binary approximation.
**Why DO NOTHING alone is insufficient.** An exact duplicate matches and adds no row. A reused UUID with a different payload fails comparison. An occupied natural key with another UUID leaves the expected UUID absent and fails. A conflict rolls back every insert and progress update in that batch. Earlier committed batches survive. Parse failure while assembling a later batch likewise leaves prior commits intact.
**Run state, not resume position.** ingestion_runs records versions, configuration, expected unique count, inserted count, status and timestamps. Batch inserts and count/status updates commit together. IngestionResult distinguishes processed lines this attempt, newly inserted rows this attempt and durable total. Completion checks total processed lines and database unique rows before marking complete; schema constraints enforce count/status/completion-time consistency. A replay can temporarily set an already-complete run back to in_progress until verified again. No offset is skipped. Compatibility SQL renames the older run_key and removes old checkpoint columns; this is not a general migration framework. finally rolls back an open failed transaction and releases the session lock. after_batch_commit and optional delay support testing after durable progress, not checkpoint recovery.

## 6. query.py: defend the calculation before the endpoint
**Cues:** validate once → select fixed SQL → bind values → aggregate → check output size.
**Say it:** “Each reading creates a bounded constant-value interval. The mean is total BPM-seconds divided by valid seconds. The same interval construction powers all five operations and the separate gap summary.”
**Shared path.** validate_query converts to QueryOperation and checks heart_rate, aware timestamps, start < end, at most 31 days and row_limit from 1–1,000. Four user operations require user-[0-9]{4}; population rejects a user ID. execute_query checks user existence, runs one allowlisted aggregation SQL statement and one allowlisted quality statement, and returns both. Request values and the configured hold are bound parameters; no user text becomes SQL. QueryResult exposes `aggregation_basis=time_weighted_observation_hold`, `max_hold_seconds`, `quality`, and rows.
**Interval CTEs.** The individual and population CTEs select readings inside the request plus the immediately preceding reading per user/device/metric. `lead(observed_at)` is calculated before state filtering. Each interval starts at the later of the reading and request start, and ends at the earliest of the next reading, original timestamp plus the configured hold, or request end. Non-positive clipped intervals disappear. Out-of-order insertion cannot change the ordered window result.
**user_period_average.** One user, all states, one row containing `time_weighted_mean_bpm` and `contributing_duration_seconds`.
**user_period_resting_average.** Same row shape, but only intervals whose originating reading is `rest`; workout or other-state readings still stop a preceding rest interval because filtering happens after `lead`.
**daily_user_average.** Rest intervals are split at the user's local-midnight instants. Date-to-instant conversion uses the IANA timezone, so elapsed seconds remain correct across DST rather than assuming 86,400 seconds.
**activity_state_comparison.** Intervals are grouped by their originating state and ordered sleep/rest/ordinary_activity/workout. States with no duration are absent.
**population_daily_average.** All-state intervals are split at UTC midnight. The numerator pools BPM × user-seconds and the denominator pools valid user-seconds. Rows also report contributing user-seconds and distinct contributing users; people are not weighted equally.
**Quality SQL.** Individual quality computes availability from all heart-rate intervals before any rest filter and includes initial, interior and final gaps. Population quality starts from every row in `users`, calculates each person's gaps independently, and aggregates user-seconds; one person's interval never covers another's. A completely missing user contributes one full-request gap. These values express availability under the hold assumption, not physiology or device uptime.
**Boundary and contribution rules.** `[start,end)` remains half-open. A still-valid carry-in reading contributes only its original remaining hold. Missing groups stay absent; zero valid duration yields no mean row while quality remains present. An unknown user raises UnknownUserError.
**Size and error rules.** The limit counts aggregated result rows, not raw observations. build_query requests row_limit + 1; execute_query rejects overflow instead of returning a silently truncated answer. The actual API test asks for two population days with row_limit=1 and receives 413, with no partial rows. The 1,000-row default ceiling is defensive and not normally reachable by these narrow daily/state aggregations. AnalyticalQueryError carries invalid_query; subclasses distinguish unknown_user and response_too_large. A period result has at most one row, so a valid limit cannot overflow it.

## 7. api.py, config.py and cli.py: adapters with explicit boundaries
**Cues:** runtime input checks; same domain path; scoped connections; configuration is not ingestion.
**Say it:** “FastAPI converts HTTP into a StructuredQuery and translates known failures into stable JSON errors. The CLI coordinates the same modules. There is no duplicate SQL inside a route, and a structured request does not need model inference.”
**HTTP input/output.** StructuredQueryRequest forbids extra fields, allowlists operations/metric, bounds row_limit and requires offset-aware RFC 3339 timestamp strings before datetime parsing. Numeric Unix timestamps and naive strings are rejected. to_domain creates StructuredQuery; domain validation still protects non-HTTP callers. NaturalLanguageQueryRequest accepts a question of 5–500 characters. DailyAverageRow, PeriodAverageRow, ActivityComparisonRow and PopulationAverageRow describe the distinct outputs; AnalyticalQueryResponse describes the envelope. The NL response additionally exposes interpreted_query and temporal_interpretation so the accepted meaning is visible.
**Connection and app lifecycle.** database_connection opens one psycopg connection, yields it through Depends and closes it in finally, including failures; there is no pool. create_app loads settings and allows planner, reference clock and relative-date zone injection for tests. app=create_app() constructs the app when imported; it does not generate or ingest data. Route decorators register handlers.
**Routes.** GET /health/live reports that the process responds. GET /health/ready checks a complete ingestion run, at least one observation and planner.available(). The last check lists the model; it does not execute inference. POST /v1/query calls execute_query directly. POST /v1/query/natural-language calls interpret_question, then the same execute_query and returns both interpretation and answer. Combined readiness can fail for a model issue even though structured analytics could work; separate core/inference readiness is future work.
**Failures and their purpose.** _error builds {error: {code, detail}} with optional fields. RequestValidationError becomes 422 invalid_request with field locations/messages/types. Analytical errors become 422, except ResponseTooLargeError → 413. Natural-language errors become 422, except ModelUnavailableError → 503. psycopg errors become 503 database_unavailable with a generic message, not credentials. These distinguish invalid meaning, excessive output and unavailable dependencies. OpenAPI documents shapes; it supplies neither identity nor authorization.
**Settings.** load_settings reads HEALTH_DATA_ variables for database URL; seed/window/days/user count; source path; batch size/delay; maximum hold; Ollama URL/model/timeout; relative-date timezone. `HEALTH_DATA_MAX_HOLD_SECONDS` defaults to 360 and must be positive. It is an analytical validity assumption, not generator behavior or a clinical threshold. Other defaults include batch size 1,000, zero delay, qwen2.5:1.5b and 30-second inference timeout; relative dates use UTC.
**CLI coordination.** main uses argparse for bootstrap, demo-queries or api. bootstrap validates/creates the source before opening PostgreSQL, applies schema and ingests, then serializes source reuse/digest and IngestionResult with asdict. demo_queries builds all five requests for the configured sample window and prints results from execute_query. serve_api imports uvicorn only when needed and serves health_data.api:app. with connect(...) manages connection lifetime. Keeping core queries independent of HTTP makes their semantics reusable and testable.

## 8. natural_language.py: a candidate plan is not trusted meaning
**Cues:** preflight → application dates → model JSON → original-question grounding → core validation.
**Say it:** “The model proposes one allowlisted operation, not SQL. JSON validation checks its shape; independent checks then verify that user, dates, grouping and rest intent still match the question. A plausible answer to a different question is rejected.”
**Preflight — _validate_question_scope.** The bounded English vocabulary requires explicit heart rate and one user or population scope. It rejects recognized unsupported metrics, instructions, medical advice, non-mean operations and unsupported dimensions. 'My' needs an explicit user because authentication is absent. No valid prefix is extracted from user-0001-extra. Recognized hourly/weekly/monthly/device grouping, combined daily/state grouping, population state filters, subsets for state comparison and non-rest daily filters are rejected. Population averages require daily wording; single-user daily rest uses local day, population daily uses UTC. Whole-period user averages allow all states or rest, not a requested workout-only mean. Regex rules are a finite interface, not perfect English understanding or comprehensive prompt-injection security.
**Dates — resolve_temporal_expression.** Accept exactly two offset-aware timestamps, or last/previous week. datetime.fromisoformat rejects impossible dates after the lexical match. Other recognized relative phrases and combining last week with explicit bounds are errors. Last week means the previous completed ISO week: Monday 00:00 to the following Monday 00:00 in the configured relative-date zone, UTC by default. It uses actual request time unless a test injects a reference. It is not the past rolling seven days and is never shifted to the fixed sample to manufacture an answer. TemporalInterpretation records kind, bounds, zone and reference time; explicit ranges have no relative zone/reference metadata.
**Model request — OllamaPlanner.** available calls /api/tags with a timeout capped at three seconds and checks the configured model name prefix. plan posts /api/generate with SYSTEM_PROMPT, ModelPlan's JSON schema, stream=False, temperature=0 and a fixed seed. The small local model avoids paid API access and keeps inference local. These options reduce variability, not guarantee correctness. _planner_question appends application-resolved relative bounds and an explicit NONE-grouping/required-operation cue for recognized whole-period requests.
**Post-model grounding — interpret_model_plan.** ModelPlan forbids extra fields and accepts only operation, user_id, heart_rate, start and end. Dates must equal the resolved instants; a single-user plan must preserve the one complete mentioned identity, population must have null and no mentioned user. Period means require average/mean without daily/state grouping and must preserve all-state versus rest intent. Daily means require explicit daily and rest intent; activity comparison requires an average comparison across activity states; population requires daily population intent. A model's daily resting substitute for an overall resting question is rejected, as is switching an explicit resting request to all states. The surviving plan passes validate_query before execute_query can run it.
**Error purpose.** NaturalLanguageError subclasses separate ambiguous_question, unsupported_metric, unsupported_operation, unsupported_question, invalid_timestamp, invalid_model_output and model_unavailable. Invalid JSON/nonobject/schema output is not accepted; HTTP or response-envelope failures become model_unavailable. interpret_question returns query plus temporal context. QueryPlanner is the small plan/available Protocol used by real and controlled planners. There is no free-form model-generated answer, arbitrary SQL or medical inference. A first inference can exceed the 30-second timeout even after model listing succeeds; a warm success does not erase that limitation.

## 9. Two concrete walkthroughs
### A. One event, a failure and replay
**Cues:** schedule → reading → retained line → transaction → exact duplicate.
**Say it:** “Imagine a day plan with wake at 07:00, bed at 22:30, workout 12:10–12:50 and device off 12:20–13:00. These are illustrative times allowed by the rules, not a claim about a particular generated user.”
At 06:59 the state is sleep. At 07:00–07:44 it is awake rest; after that ordinary activity applies until another rule wins. Lunch rest starts at 12:00, but the workout overrides it at 12:10. Off overrides workout from 12:20. If the cursor lands there, no event is emitted; it jumps to after 13:00 with the extra 1–30 seconds. At that next instant lunch rest has ended and the workout is over, so ordinary activity normally resumes. Evening rest is 18:30–19:30; the final pre-bed rest starts at 21:45 and sleep at 22:30. Cursor steps mean the first observed reading in a state can be after its boundary.
For an on-device cursor, generate_events calculates BPM, creates HeartRateEvent and yields it. publish_source writes its JSON line and publishes the completed source pair. On initial ingestion, read_events checks its fields/identity, _event_values maps it to bound SQL and the batch transaction inserts it and updates run progress together.
If a callback interrupts after a committed batch, those observations and their count survive. Retry's ensure_source validates the same published files without generating events. ingest rereads the first line, verifies duplicate content and adds only missing observations. Changing batch size does not change which offsets are skipped because no offsets are skipped. If a duplicate's value differs, the conflicting batch rolls back instead of quietly accepting it; retained earlier batches remain. Losing the source volume is outside this recovery guarantee.
### B. One question, all five meanings
**Cues:** same interval, different contribution/grouping rules.
Use the focused fixture with 60 BPM at 00:00, 120 at 00:02 and 90 at 00:06 over a ten-minute request. The intervals contribute 120, 240 and 240 seconds. The result is `(60×120 + 120×240 + 90×240) / 600 = 96.0 BPM`, not the arithmetic sample mean 90.0. A rest reading followed by a workout reading two minutes later contributes only those two rest minutes even though the state filter excludes the workout from the rest mean. A reading five minutes before `start` can contribute one remaining minute under a six-minute hold; after that it is expired. Separate fixtures split intervals at local and UTC midnight, verify 23- and 25-hour DST days, expose initial/interior/final gaps, and pool population user-seconds with different observed durations.
For “average resting heart rate” without daily wording, preflight/date resolution leads to the required user_period_resting_average cue. If the model proposes daily_user_average, grounding rejects it. With a correct plan, HTTP uses the same SQL path as the structured request and exposes the accepted interpretation. Ask outside the stored dates and a valid request returns empty rows, not a shifted period or fabricated zero.

## 10. Running, verifying and answering follow-ups
**Cues:** terminating setup jobs; separate retained volumes; tests prove specific guarantees.
**Say it:** “The deployment separates database, source and model persistence. Tests isolate deterministic correctness from real-model behavior. The five operations share the same tested query engine; the CLI, HTTP and natural-language adapters preserve their meanings.”
**Build and startup.** pyproject.toml uses setuptools, src discovery and Python >=3.11; direct dependencies pin FastAPI/Pydantic, psycopg, httpx, tzdata and uvicorn. Dockerfile uses Python 3.12.7, copies pyproject/src/sql, installs the package, sets HEALTH_DATA_SCHEMA_PATH=/app/sql/schema.sql, prepares source storage and runs as UID 65532. db.py otherwise derives the schema path from its source layout, with the environment override needed for the image's installed layout. .dockerignore excludes tests/scripts/docs and development artifacts; .gitignore excludes caches, environments/build products and .env. Ignore rules are not secret management.
**Compose dependency flow.** PostgreSQL 16.6 retains observations in postgres-data; Ollama retains weights in ollama-data; bootstrap retains JSONL in source-data. PostgreSQL health gates bootstrap. Ollama health gates the terminating model-init pull job. api waits for successful bootstrap and model-init, serves on loopback port 8000 and uses combined readiness for its healthcheck. bootstrap/model-init are jobs, not ongoing producers. Normal container replacement retains volumes; down --volumes deletes them. These volumes are not backups. No authentication, per-person authorization or TLS is implemented.
**Tests by responsibility.** test_generator checks deterministic payloads/IDs, population/profile variation, contract/range, state patterns, cadence variation and off gaps. test_source checks round trips, failed publication, reuse without generator calls, incompatible input and line-specific failures. test_ingestion uses real PostgreSQL for replay, committed progress, changed batch sizes, exact duplicates, conflicts, ordering and constraints. test_query uses hand-calculated value-seconds for unequal intervals, state changes, carry-in expiry, initial/interior/final gaps, missing data, local/UTC midnight, DST, population user-seconds and out-of-order insertion. test_api checks the response and OpenAPI quality contracts. test_natural_language checks grounding and rejects recognized requests for another aggregation.
**Scripts and evidence.** evaluate_natural_language.py reads the 30-case manifest: eight supported questions reach the real model, twenty are rejected at preflight and two faults are covered separately by isolated tests. Successful NL results are compared with the entire structured result JSON. clean_start_e2e.sh checks health, both interfaces, replay and restart. test_interrupted_ingestion.sh retains its persisted-source recovery role. Dated verification documents state which query semantics each run exercised.
**Likely questions.** Why 360 seconds? It bounds stale carry-forward and makes gaps visible; it is configurable and must be justified for a real source. Why no interpolation?
